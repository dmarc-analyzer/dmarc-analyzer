# Contributing to DMARC Analyzer

Thanks for taking the time to contribute. This file is the short version —
the full developer guide is **[`docs/DEVELOPMENT.md`](docs/DEVELOPMENT.md)**.

## Before you start

- Check open [issues](https://github.com/dmarc-analyzer/dmarc-analyzer/issues)
  and [pull requests](https://github.com/dmarc-analyzer/dmarc-analyzer/pulls)
  to avoid duplicate work.
- For a non-trivial change (new feature, breaking change, schema migration,
  API surface change), please **open an issue first** to discuss the approach
  before sinking time into a PR.
- For tiny fixes (typos, dead links, single-file refactors) just send the PR.

## Ground rules

- **Code is licensed Apache 2.0** (see [`LICENSE`](LICENSE)). By submitting a
  PR you agree your contribution is licensed under the same terms.
- Be respectful in discussions; concise is more valuable than clever.
- If your change touches user-visible behaviour, update the relevant docs in
  the same PR.

## Local setup (TL;DR)

```sh
# Go
go version                # need 1.25+
createdb dmarc_analyzer
psql -d dmarc_analyzer -f backend/schema.sql

# Backend dev loop
DATABASE_URL='postgres://localhost:5432/dmarc_analyzer?sslmode=disable' \
  go run ./backend/cmd/server/server.go

# Frontend dev loop (in another terminal)
cd frontend
yarn install
yarn dev                  # http://localhost:3000, proxies /api to :6767
```

Full step-by-step including AWS-less ingestion (manual JSON insert),
backfill, and tests: **[`docs/DEVELOPMENT.md`](docs/DEVELOPMENT.md)**.

## Code style

| Language   | Standard |
|------------|----------|
| Go         | `gofmt`. Package names lowercase, exported identifiers `CamelCase`. |
| TypeScript | `eslint` with `@antfu/eslint-config`. Run `cd frontend && yarn lint --fix`. |
| Vue        | PascalCase filenames (`DetailDialog.vue`). |
| SQL        | Lowercase keywords; snake_case identifiers. Generated, see below. |
| Docs       | Markdown, 80-ish column wrap, code blocks fenced with language hints. |

## Tests

Run before opening a PR:

```sh
# Go tests (some require a local Postgres)
DATABASE_URL='postgres://localhost:5432/dmarc_analyzer?sslmode=disable' \
  go test ./...

# Frontend build (also runs vue-tsc type checks)
cd frontend && yarn build
```

There is currently no frontend test runner. If you add one, wire a `test`
script in `frontend/package.json` and document it in
[`docs/DEVELOPMENT.md`](docs/DEVELOPMENT.md).

## Spec-first API workflow

The Gin route table and the TypeScript axios client are **generated** from
[`api/openapi.json`](api/openapi.json). If you add or modify an endpoint:

1. Edit `api/openapi.json`.
2. Regenerate the Go side:
   ```sh
   ./scripts/gen-routes.sh
   # or: go generate ./backend/handler
   ```
   This requires `openapi-generator` (`brew install openapi-generator`, or
   the Docker shim used in CI — see `.github/workflows/openapi-routes.yml`).
3. Regenerate the TS client:
   ```sh
   cd frontend && yarn openapi:gen
   ```
4. Update business logic in `backend/handler/handler.go` and the frontend in
   `frontend/src/services/dmarcService.ts` + `frontend/src/stores/dmarcStore.ts`.

CI rejects drift between the spec and the generated Go files (see
`.github/workflows/openapi-routes.yml`), so you'll get a clear failure if
you forget step 2.

## Schema changes

`backend/schema.sql` is **generated** from the GORM model. If you change
`backend/model/dbmodel.go`:

```sh
dropdb --if-exists gen_sql && createdb gen_sql
go run ./backend/cmd/generate_sql.go
echo '-- Code generated by dmarc-analyzer generate_sql. DO NOT EDIT.' > backend/schema.sql
pg_dump -d gen_sql --schema-only --no-owner \
  | sed '/^--/d' \
  | sed '/^SET /d' \
  | sed '/^SELECT /d' \
  | sed 's/public\.//g' \
  | sed -e :a -e '/^\n*$/{$d;N;ba' -e '}' -e 's/\n\n*/\n/' \
  >> backend/schema.sql
dropdb --if-exists gen_sql
```

The application does **not** auto-migrate at runtime. In your PR
description, list the manual SQL operators must run to migrate existing
databases.

## Commit messages

- Short, imperative ("add foo", not "added foo" or "adds foo").
- Conventional prefixes when natural: `fix:`, `feat:`, `docs:`, `ci:`,
  `refactor:`, `chore:`, `test:`.
- Sign-off (`-s`) and GPG-sign (`-S`) when you can:

  ```sh
  git commit -s -S -m "fix: handle empty <record> element in DMARC XML"
  ```

  Sign-off declares the [Developer Certificate of Origin](https://developercertificate.org/);
  GPG signing proves the commit is yours.

## Pull requests

A good PR has:

- **A clear title** in the same style as commit messages.
- **A body** explaining *why* (link to the issue if there is one). The
  *what* is in the diff; the *why* often isn't.
- **A scope you can defend**. Don't bundle three unrelated changes; split
  them.
- **Updated docs** if behaviour or surfaces changed.
- **Tests** for backend logic where it's reasonable to add them.
- **Screenshots** (before/after) for any visible frontend change.

The PR template (if one exists) covers most of this. If a checklist item
genuinely doesn't apply, mark it N/A — don't silently skip.

## Reporting bugs

Open an issue with:

- Version (image tag or commit SHA you're running).
- Steps to reproduce — the exact SES setup is fine even if it's "the
  example in docs/DEPLOYMENT.md".
- Expected vs actual behaviour.
- Relevant log snippets (sanitize anything sensitive).
- For parsing bugs: an example `.eml` (with PII redacted) and the resulting
  log line is gold.

## Suggesting features

Open an issue describing:

- The problem you're trying to solve (not the solution).
- Who would benefit and how often.
- One or two solution sketches if you have them.

For larger features (e.g. failure report parsing, TLSRPT, alternative
ingestion paths) please open the issue before writing code so we can agree
on scope.

## Security issues

If you find a security issue, **please don't open a public issue**. Email
the maintainers privately (find an address in `git log` or via a GitHub
profile contact). We'll respond within a few business days.
